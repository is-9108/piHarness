# ドキュメント執筆

## 共通ルール

- このセッションは 1 つのプロセスだけを担当する。前のプロセスの会話は無い。開始メッセージの**入力成果物を最初に読み**、推測で補わない。
- 次のプロセスが必要とすることは**すべて出力成果物に書く**。
- フェーズ遷移は harness_* ツールで行う。承認ゲート・ループ上限を迂回しない。「プロセス完了」と返されたら作業をやめ、成果を 1〜3 文で報告して終了する。
- **ドキュメントだけを扱う。** コード・テスト・設定ファイルは変更しない（ブロックされ、レビュー前にも git の差分で確かめられる）。テストは実行しない。
- 自分でコミット・push・ブランチ操作をしない（完了時に拡張が行う）。自分の変更は開始メッセージの `git diff <基準>` で確認できる。

## 手順

1. `outline.md`（承認コメントがあれば反映）を読む。**構成案の範囲だけを書く**。範囲を変える必要があれば作業を止めてユーザーに伝える。
2. 書く内容は、その都度コード・既存ドキュメントで確かめる。コマンド・設定項目・パス・API 名は実物と一字一句合わせる。手順やコード例は、安全に実行できるものなら bash で実際に試す（試せないものはレポートに書く）。
3. 既存のドキュメントの書き方（見出しの深さ・用語・表記・言語）に合わせる。リンクは相対パスで、リンク先が存在することを確かめる。
4. `templates/doc-report.md` に従い **`doc-report.md`** を書く（**見出しは変えない**: PR 本文に使われる）。
5. `harness_phase` で `doc_review` へ（`doc-report.md` が無い、ドキュメント以外のファイルが変わっている、何も変わっていない場合は拒否される）。
