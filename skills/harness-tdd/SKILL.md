# TDD 実装フロー（piHarness）

piHarness 拡張がフェーズ・承認・ループ回数を管理しています。現在の状態は `harness_status` で確認できます。
**承認ゲートとループ上限を迂回しないこと**（テストを弱める・スキップする・削除して合格させるのも迂回です）。

## セッションと成果物の原則

各プロセスは**独立したセッション**で実行されます。前のプロセスの会話は引き継がれず、**作業ディレクトリ（例: `.pi/harness/issue-12/`）の md ファイルだけ**が引き継がれます。

- セッション開始時のメッセージに列挙された**入力成果物をすべて読んでから**作業を始める。記憶や推測で補わない。
- 次のプロセスが必要とする情報は、**すべて出力成果物に書く**（書かなかったことは次のセッションに伝わらない）。
- プロセスが完了すると拡張が自動で次のセッションを開始します。「プロセス完了」と返されたら、それ以上作業せず短く報告して終了してください。

| プロセス（セッション） | フェーズ | 入力 | 出力 |
|---|---|---|---|
| プラン作成 | impl_context → impl_plan → 承認 | `issue.md` | `plan.md` |
| TDD 実装 | impl_tdd | `issue.md`, `plan.md` | コード + `implementation.md` |
| コードレビュー | impl_review | `issue.md`, `plan.md`, `implementation.md`, 過去の `review-*.md` / `fix-*.md` | `review-N.md`（skill harness-review） |
| レビュー指摘修正 | impl_fix_review | `review-N.md`, `plan.md`, `implementation.md` | コード + `fix-N.md` |

## 1. Issue とコードベースの読み込み（impl_context）

まだコードを変更してはいけません（拡張が作業ディレクトリ以外への書き込みをブロックします）。

1. `issue.md`（背景・スコープ・**受け入れ条件**・テスト観点・参照ドキュメント）を読む。本文が取得できていなければ `gh issue view <番号>` または `docs/issues/` から取得して `issue.md` に保存する。
2. 参照されている要件定義書・設計書（`docs/requirements/`, `docs/design/`）を読む。
3. コードベースを調査する:
   - ディレクトリ構成、エントリポイント、変更対象になりそうなモジュールと呼び出し元
   - 既存テストの場所・フレームワーク・命名規則・モックの流儀
   - Lint/フォーマッタ設定、コーディング規約（AGENTS.md / CONTRIBUTING.md 等）
   - テストコマンド（`/harness config` で確認できる testCommand）
4. Issue の記述が曖昧・矛盾している場合は `harness_ask` でユーザーに確認する。
5. `harness_phase` で `impl_plan` へ（note に調査結果の要約）。

## 2. テストプランと実装プラン（impl_plan）

`templates/plan.md` に従い、作業ディレクトリの **`plan.md`** を作成する。**実装セッションはこのファイルと issue.md しか読まない**ので、調査結果（変更対象・既存テストの流儀・影響範囲）も必ず書く。

- **テストプラン**: 受け入れ条件ごとにテストケースを列挙（正常系・異常系・境界値）。テストの種類（ユニット/結合）、置き場所、モック対象を明記。
- **実装プラン**: 変更ファイル・追加する関数/クラス・手順（テストケースとの対応）。Raspberry Pi 5 上での性能・メモリへの影響も記載。
- **スコープ外**: Issue の範囲外で気づいたことは書き出すだけにして実装しない。

`harness_request_approval`（`kind: "plan"`, `documents: ["<作業ディレクトリ>/plan.md"]`）で承認を依頼する。
- 修正依頼 → 反映して再依頼。
- 保留 / UI なし → 作業を止めて `/harness approve` を待つ。
- 承認 → このセッションは終了し、TDD 実装は新しいセッションで始まる。

## 3. TDD 実装（impl_tdd）

`issue.md` と承認済みの `plan.md` を読み、テストケースを 1 つずつ次のサイクルで進める:

1. **Red**: 失敗するテストを 1 つ書く → `harness_run_tests`（`expect: "red"`）。
   - 失敗理由が「未実装」によるものであることを確認する（構文エラーや import ミスによる失敗は Red とみなさない）。
   - 合格してしまったら、テストが振る舞いを捉えていない。テストを見直す。
2. **Green**: テストを通す最小限の実装を行う → `harness_run_tests`（`expect: "green"`）。
3. **Refactor**: 重複除去・命名改善。振る舞いは変えない → `harness_run_tests`（`expect: "green"`）。

個別テストだけを速く回したい場合は bash で直接実行してよい。ただしループ判定・フェーズ遷移に使われるのは `harness_run_tests`（スイート全体）の結果のみ。

- **green 判定にはチェックも含まれる**: `.pi/harness.json` の `checkCommands`（lint・型チェックなど）が設定されていれば、`expect: "green"` のときテストに続けて実行され、**すべて合格して初めて合格**です。チェックの失敗も修正ループの 1 回に数えます。
- **合格後の変更は検知される**: 最後の合格後にファイルを変更すると（edit/write だけでなく bash の `sed -i` やコード生成も含め、git で検知）、テストを再実行するまで次へ進めません。
- **テストを弱めると止められる**: 実装開始時点からの差分で、テストファイルの削除・`.skip`/`xit`/`@pytest.mark.skip` 等の追加・`.only` 等の追加・アサーションの減少を検知すると、レビューへの遷移が拒否されます。
  意図しない変更なら元に戻す。仕様変更で不要になったテストの削除など**正当な理由がある場合だけ** `harness_phase` の `testChangeReason` に理由を書いて再実行する（理由は `test-changes.md` に記録され、レビュー担当が検証します）。

### Git について

- `/impl` 開始時に拡張が作業ブランチ（例: `issue-12-add-login`）を作成し、開始時点のコミットを差分の基準として記録しています。開始メッセージの「変更の差分」の案内に従い `git diff <基準>` で自分の変更を確認できます。
- **自分でコミット・push・ブランチ切り替えをしない**（完了時に拡張がコミットし、設定に応じて PR を作成します）。

### テスト失敗時のループ（最大 3 周）

`expect: "green"` での失敗は修正ループとして数えられます。毎回、以下を**明示的に書いてから**修正する:

1. 失敗したテスト名とエラーメッセージ（全文ログは作業ディレクトリの `logs/`）
2. 根本原因の仮説（なぜそうなるか）と、それを確かめる方法
3. 仮説の確認結果
4. 最小限の修正内容 → `harness_run_tests` を再実行（`reason` に 1〜4 の要約）

同じ修正を繰り返さないこと。前回の仮説が外れたら別の角度から分析する。
**連続 3 回失敗するとユーザーへエスカレーション**されます（記録は `escalation-N.md`）。表示された選択（ループ継続 / バグ修正フロー / 手動対応 / 中止）に従い、手動対応・中止の場合は作業を止めて状況を報告します。

### 完了条件と実装レポート

プランの全テストケースが実装済みで、最後の `harness_run_tests`（green）が合格し、その後ファイルを変更していないこと。
`templates/implementation.md` に従い **`implementation.md`** を書く（レビュー担当は別セッションで、このレポートと差分だけを見てレビューします）。
→ `harness_phase` で `impl_review` へ（`implementation.md` が無いと拒否されます）。

## 4. コードレビュー（impl_review）

別のセッションで skill `harness-review` が担当します。

## 5. レビュー指摘の修正（impl_fix_review）

1. 最新の `review-N.md` を読み、ブロッキング指摘（blocker/major）を把握する。`plan.md` と `implementation.md` で背景を確認する。
2. 指摘ごとに修正する。指摘が誤っていると判断した場合は、根拠を `fix-N.md` に書く（黙って無視しない）。
3. `harness_run_tests`（green）で全テストを合格させる（テスト失敗ループは最大 3 周）。
4. `templates/fix-report.md` に従い **`fix-N.md`**（N はレビュー周回）に指摘ごとの対応を書く。**次のレビューは軽量レビューで、主にこのファイルを見て解消を確認します。**
5. `harness_phase` で `impl_review` へ（`fix-N.md` が無いと拒否されます）。

レビューが **3 周してもブロッキング指摘が残る場合はユーザーへエスカレーション**されます。

## 6. 完了報告（impl_done）

レビューセッションで完了すると、拡張が Issue を完了にし、変更をコミットし、設定（`git.pr`）に応じて確認のうえ PR を作成します。以下をユーザーに報告する:
- 変更したファイルと概要、Issue の受け入れ条件ごとの充足状況
- テスト結果（最終実行ログのパス）
- レビュー結果（`review-*.md`）と、残した minor/nit 指摘（必要なら別 Issue 化を提案）
- コミット・PR の結果（PR を作成しなかった場合は `/harness pr` で後から作成できること）とモデル利用量
- 次の Issue は `/impl next` で開始できること

## バグ修正フローからの合流

エスカレーション後にユーザーがバグ修正フロー（`harness-bugfix`）を選んだ場合、完了後に新しいレビューセッションで合流します。バグ修正でコードが変わっているため、合流後はフルレビューから再開します。
