# 設定変更

設定ファイル（`.pi/`・CI・lint・フォーマッタ・パッケージの設定値・`.env.example` など）を変えるだけの作業。**テストもレビューも無い**ので、計画の承認が唯一の確認になる。

## 共通ルール

- このセッションは 1 つのプロセスだけを担当する。前のプロセスの会話は無い。開始メッセージの**入力成果物を最初に読み**、推測で補わない。
- フェーズ遷移は harness_* ツールで行う。承認ゲートを迂回しない。
- 自分でコミット・push・ブランチ操作をしない（完了時に拡張が行う）。

## 計画（cfg_plan、ファイルはまだ変えない）

1. 依頼（または `issue.md`）を読み、対象の設定ファイルと、その設定を読むコード・ドキュメントを調べる（キー名・値の形式・既定値を実物で確かめる）。分からないことは `harness_ask`。
2. `templates/change-plan.md` に従い **`change-plan.md`** を書く。変更前と変更後の値を具体的に書く（承認者はこれだけを見て判断する）。
3. `harness_request_approval`（`kind: "change"`、`documents`: `change-plan.md`、**`files`: 変更するファイルをすべて**）。承認されるとこのファイル以外は変更できない。修正依頼なら計画を直して再依頼。
4. コード（`.ts` `.py` など）の変更が必要だと分かったら、この計画には入れず、作業を止めてユーザーに伝える（実装フローで行う）。

## 変更（cfg_apply）

1. 承認された計画どおりに、承認されたファイルだけを変更する（ほかはブロックされる）。計画に無い変更を足さない。
2. 変更したファイルが読めるか確かめる（例: JSON・YAML の構文、ツールに設定の検証コマンドがあれば実行）。
3. `harness_phase` で `cfg_done` へ。拡張が「変更が承認されたファイルだけか」「JSON が壊れていないか」を git の差分で確かめ、コミットと PR の作成まで行う。拒否されたら直して再度進める。
4. 変更したファイルとコミット/PR の結果を 1〜3 文で報告して終了する。
