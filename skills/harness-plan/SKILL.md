# テスト/実装プラン作成

まだコードを変更しない（作業ディレクトリ以外への書き込みはブロックされる）。

## 共通ルール

- このセッションは 1 つのプロセスだけを担当する。前のプロセスの会話は無い。開始メッセージの**入力成果物を最初に読み**、推測で補わない。
- 次のプロセスが必要とすることは**すべて出力成果物に書く**。
- フェーズ遷移は harness_* ツールで行う。承認ゲート・ループ上限を迂回しない。「プロセス完了」と返されたら作業をやめ、成果を 1〜3 文で報告して終了する。
- **重要な設計判断をしたら `harness_record_decision` で ADR を記録する**（対象はツールの説明のとおり）。判断の前に開始メッセージの ADR 一覧で関連するものを確認して従い、変えるなら `supersedes` で置き換える。成果物からは ADR 番号で参照する。

## 手順

1. `issue.md`（受け入れ条件）を読む。本文が無ければ `gh issue view <番号>` 等で取得して `issue.md` に保存する。参照先の要件定義書・設計書も読む。
2. コードを調査する: 変更対象と呼び出し元、既存テストの場所・フレームワーク・モックの流儀、規約（AGENTS.md 等）、テストコマンド（`/harness config`）。
   Issue が曖昧・矛盾していれば `harness_ask`。
3. `harness_phase` で `impl_plan` へ。
4. `templates/plan.md` に従い **`plan.md`** を書く。実装セッションは `issue.md` と `plan.md` しか読まないので、調査結果も書く。
   - テストプラン: 受け入れ条件ごとに正常系・異常系・境界値。種類・置き場所・モック対象。
   - 実装プラン: 変更ファイル・手順とテストケースの対応。Pi 5 での性能・メモリへの影響。スコープ外は書き出すだけ。
   - **テストケースが 12 件を超える・変更が 300 行を大きく超えそうなら、Issue の分割をユーザーに提案する**（`harness_ask`）。1 セッションで扱える大きさに保つため。
5. `harness_request_approval`（`kind: "plan"`）。修正依頼なら反映して再依頼。保留なら `/harness approve` を待つ。承認後の実装は新しいセッションで行われる。
