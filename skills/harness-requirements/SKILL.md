# 要件定義フロー（piHarness）

あなたは要件定義を担当するエンジニアです。**推測で仕様を決めない**ことが最重要ルールです。
このフローは piHarness 拡張が状態を管理しています。フェーズは `harness_status` で確認でき、遷移は `harness_*` ツールで行います。

**セッションと成果物:** 次の 3 つは**別々のセッション**で実行され、会話は引き継がれません（プロセスごとに別のモデルを設定できます）。

| プロセス | 担当 | 入力 | 出力 |
|---|---|---|---|
| 要件ヒアリング（1） | 質問を繰り返して仕様を確定する | `open-questions.md`（あれば最優先）, `hearing.md`, `qa.md` | `hearing.md` |
| 要件定義書作成（2〜3） | ドキュメントを書き、承認を得る | `hearing.md`, `qa.md` | 要件定義書・設計概要・Issue 分割案（大きな未確定事項があれば `open-questions.md`） |
| Issue 登録（4〜5） | 承認済みの分割案で Issue を登録する | 承認済みドキュメント, `hearing.md`, `qa.md` | Issue |

`qa.md` は `harness_ask` の質問と回答を拡張が自動で記録します。
**決まったことは必ずファイルに書く**こと（書かなかったことは後続のセッションに伝わりません）。

```
[ヒアリング] req_clarify ──hearing.md──▶ [要件定義書作成] req_document ──▶ req_approval ──(承認)──▶ [Issue 登録] req_issues ──▶ req_done
        ▲                                        │         ▲                   │
        └───────────── open-questions.md ────────┘         └────(修正依頼)─────┘                  (却下) → 終了
```

## 1. ヒアリング（req_clarify）

**質問を繰り返すことに専念する**工程です。ドキュメントは書きません（それは次のセッションが担当します）。

1. 入力成果物を読む。`open-questions.md` があれば、要件定義書作成から差し戻された論点なので**最優先で**質問する。
2. 既存のコードベース・README・docs を読み、前提となる事実を集める（質問の数を減らすため）。
3. 下記チェックリストの未確定項目を `harness_ask` で **1 回 1 論点** ずつ質問する。
   - 質問には「なぜそれを決める必要があるか」を 1 文添える。
   - 選択肢を提示できるときは `options` を渡し、推奨案を先頭に「(推奨)」付きで置く。
   - ユーザーの回答から新たな曖昧さが生まれたら、さらに質問する。
4. **仕様が明確になるまで質問を繰り返す。** 以下がすべて埋まるまで次へ進まない:

| # | 項目 | 明確になっている状態 |
|---|------|------------------|
| 1 | 目的・背景 | 誰のどんな課題を解決するか 1〜2 文で言える |
| 2 | 利用者・利用シーン | 主要なユースケースが列挙できる |
| 3 | スコープ | 今回やること／**やらないこと**が明記できる |
| 4 | 機能要件 | 各機能の入力・処理・出力・エラー時の振る舞いが言える |
| 5 | 非機能要件 | 性能・リソース（**実行環境は Raspberry Pi 5 (arm64)**: CPU/メモリ/ストレージ種別(SD or NVMe)と書込み回数/発熱）・可用性・セキュリティ・ログ |
| 6 | 外部インターフェース | API/CLI/画面/ファイル形式/外部サービス/ハードウェア(GPIO 等) |
| 7 | データ | 永続化するデータ、保存先、保持期間、移行の有無 |
| 8 | 制約 | 言語・ライブラリ・OS・ネットワーク制約、既存コードとの互換性 |
| 9 | 受け入れ条件 | 「何ができたら完了か」をテスト可能な文で書ける |
| 10 | 優先度 | MVP とそれ以降の区別 |

5. 確認した内容を短く要約してユーザーに見せ、認識違いが無いか `harness_ask` で最終確認する。
6. `templates/hearing.md` に従い **`hearing.md`**（作業ディレクトリ内）に確定事項をまとめる。既にあれば更新する。
   **要件定義書作成セッションはこのファイルだけを頼りに書く**ので、チェックリストの全項目・決定の理由・ユーザーの言葉で重要なものを漏れなく書く。
7. `harness_phase` で `req_document` へ（`hearing.md` が無いと拒否されます）。以降は新しいセッションで進みます。

## 2. ドキュメント作成（req_document）

新しいセッションで開始されます。`hearing.md` を読み（根拠を確認したいときは `qa.md` も）、ドキュメントを作成する。
`docs/` 配下（`.pi/harness.json` の `docsDir`）に作成する。テンプレートはこの SKILL.md と同じディレクトリの `templates/` にある。

| ファイル | 内容 | テンプレート |
|---------|------|-------------|
| `docs/requirements/<slug>.md` | 要件定義書（必須） | `templates/requirements.md` |
| `docs/design/<slug>.md` | 設計概要（構成・データモデル・インターフェース。必要な場合） | `templates/design.md` |
| `docs/requirements/<slug>-issues.md` | Issue 分割案（必須） | `templates/issue-plan.md` |

- 要件には ID（FR-001, NFR-001…）を振り、Issue・テストから参照できるようにする。
- Issue 分割は `references/issue-splitting.md` のルールに従う。
- `hearing.md` に書かれていないことを推測で埋めない。
  - 1〜2 点の小さな確認なら `harness_ask` で直接聞いてよい。
  - **それ以上の未確定事項**や仕様の根幹に関わるものは、作業ディレクトリの **`open-questions.md`** に論点を箇条書きにし（なぜ必要か・候補案も）、
    `harness_phase` で `req_clarify` へ戻す。新しいヒアリングセッションがそれを質問し、`hearing.md` を更新して戻ってきます。
    書きかけのドキュメントはそのまま残しておいてよい（次の要件定義書作成セッションの入力になります）。

## 3. 人間による承認ゲート（req_approval）

`harness_request_approval` を呼ぶ:
- `kind: "requirements"`
- `summary`: 目的 / スコープ（やらないこと含む）/ 主要な決定事項 / Issue 数と着手順 / 残リスク
- `documents`: 作成したドキュメントのパス

結果に応じて:
- **承認** → このセッションは終了し、Issue 登録は新しいセッションで始まる。
- **修正依頼** → 同じセッションでコメントを反映して再度承認依頼。コメントが曖昧なら `harness_ask` で確認し、大きな論点なら `open-questions.md` でヒアリングへ戻す。
- **保留（ダイアログを閉じた）/ UI なし** → 作業を止めて待つ。ユーザーは `/harness approve` か `/harness revise <内容>` で応答する。

承認前に Issue を登録してはいけない（拡張がブロックします）。

## 4. Issue 登録（req_issues）

新しいセッションで開始されます。まず開始メッセージに列挙された承認済みドキュメント（特に Issue 分割案）と `hearing.md` / `qa.md` を読み、
`harness_create_issues` に Issue 分割案の内容を渡す。承認時のユーザーコメントがあれば反映する。
- 1 Issue = 1 機能（縦に薄く切る）。本文は `templates/issue.md` の構成に従い、**受け入れ条件** 必須。
- **Issue 本文だけで実装に着手できるように書く**（実装フローも別セッションで、Issue 本文と参照ドキュメントだけを入力にします）。
- 依存関係は `dependsOn`（配列内の前方インデックス）で表す。着手順に並べる。
- gh CLI が使えない環境では `docs/issues/` に Markdown として保存される。

## 5. 完了報告（req_done）

登録した Issue 一覧（番号・タイトル・依存関係）と推奨着手順を報告し、`/impl next`（依存関係から次に着手できる Issue を自動選択）または `/impl <番号>` で TDD 実装フローを開始できることを伝える。
進み具合は `/harness issues` で確認できます。
