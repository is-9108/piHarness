# Issue 分割ルール

目的: **1 Issue を 1 回のレビューで無理なく読み切れる大きさにする。**

## 原則

1. **1 Issue = 1 機能（1 つの受け入れ可能な振る舞い）**。「〜と〜を実装」のように「と」が入るなら分割を検討する。
2. **縦に切る**（UI → ロジック → 永続化を 1 機能分だけ貫通させる）。「DB 層を全部」「画面を全部」のような横切りは避ける。
3. **差分の目安は 300 行以下**（テスト含む）。超えそうなら、さらに小さな振る舞いに分ける。
4. **単体でテスト可能・マージ可能**であること。未完成機能はフラグや未公開 API にして、main を壊さない。
5. **受け入れ条件を必ず書く**（テスト可能な文。これが TDD のテストプランの起点になる）。
6. 依存関係は明示し、依存の少ないものから着手できる順に並べる。
7. 基盤整備（プロジェクト雛形、CI、共通ユーティリティ）が必要なら、最初の小さな Issue として独立させる。

## 分割の例

悪い例: 「温度ロガーを実装する」（1 Issue）

良い例:

| # | タイトル | 依存 |
|---|---------|------|
| 0 | センサー読み取りインターフェースとモック実装を追加 | - |
| 1 | 温度を一定間隔で取得してメモリに保持する | 0 |
| 2 | 取得値を SQLite に保存する（書き込みはバッチ化） | 1 |
| 3 | 直近 24 時間の値を返す CLI コマンドを追加 | 2 |
| 4 | systemd ユニットファイルと起動手順を追加 | 1 |

## ラベルの目安

- `feature` / `infra` / `docs` / `test`
- 優先度: `priority:must` / `priority:should`
