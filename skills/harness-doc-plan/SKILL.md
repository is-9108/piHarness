# ドキュメントの構成案作成

まだドキュメントを書かない（作業ディレクトリ以外への書き込みはブロックされる）。

## 共通ルール

- このセッションは 1 つのプロセスだけを担当する。前のプロセスの会話は無い。開始メッセージの**入力成果物を最初に読み**、推測で補わない。
- 次のプロセスが必要とすることは**すべて出力成果物に書く**。
- フェーズ遷移は harness_* ツールで行う。承認ゲート・ループ上限を迂回しない。「プロセス完了」と返されたら作業をやめ、成果を 1〜3 文で報告して終了する。
- **ドキュメントだけを扱う。** コード・テスト・設定ファイルは変更しない（ブロックされ、レビュー前にも git の差分で確かめられる）。テストは実行しない。

## 手順

1. 依頼（テーマ、または `issue.md`）を読む。読者・目的・範囲が分からなければ `harness_ask` で聞く（1 回に 1 論点）。
2. 情報源を調べる: 関係するコード（実際の振る舞い・設定項目・コマンド）、既存のドキュメント（README・docs/）、ADR 一覧。**書く内容の根拠はここで確かめる**（推測で書かない）。既存のドキュメントと重複・矛盾するものも探す。
3. `templates/outline.md` に従い **`outline.md`** を書く。執筆は別セッションで `outline.md` だけを見て行うので、各章に書く内容と根拠（ファイル:行）を書く。
4. `harness_request_approval`（`kind: "outline"`、`documents`: `outline.md`）。修正依頼なら反映して再依頼。承認後の執筆は新しいセッションで行われる。
