# アーキテクチャ

## 構成

```text
piHarness/
├── package.json                  # Pi パッケージ定義（pi.extensions / pi.skills）
├── .pi/
│   ├── settings.json             # このリポジトリで pi を起動したときに本パッケージを読み込む
│   └── harness.json              # piHarness 設定（対象プロジェクトごとに置く）
├── extensions/harness/
│   ├── index.ts                  # Pi との接続: ツール・コマンド・イベントハンドラ・UI
│   ├── state.ts                  # 状態機械（純粋関数）: フェーズ・承認・ループ回数・エスカレーション・合流
│   ├── guard.ts                  # フェーズごとの書き込み/コマンド制限（純粋関数）
│   ├── handoff.ts                # プロセス（セッション）間の引き継ぎ: 成果物パス・入出力・開始メッセージ
│   ├── guidance.ts               # 各ターンでエージェントに注入する「現在地と次の行動」
│   ├── config.ts                 # .pi/harness.json の読み込み、テストコマンド自動検出
│   ├── issues.ts                 # Issue 案の検証、gh 引数の組み立て、出力解析
│   ├── git.ts                    # 作業ブランチ・作業ツリーの指紋・差分・コミット
│   ├── integrity.ts              # テストを弱める変更の検知
│   ├── progress.ts               # Issue の進み具合と次の Issue の選択
│   ├── usage.ts                  # モデル利用量の集計
│   ├── tools.ts                  # プロセスごとに有効にするツール
│   ├── compaction.ts             # しきい値による自動圧縮の判断と要約の指示
│   ├── dashboard.ts              # TUI のダッシュボード（工程・いまの作業・ブランチ・トークン）
│   └── text.ts                   # 整形ヘルパー
├── scripts/install.mjs           # プロジェクトへの組み込み（.pi/settings.json・harness.json・.gitignore）
├── templates/harness.json        # 組み込み時に作る .pi/harness.json の雛形
├── skills/
│   ├── harness-requirements/     # 要件定義の手順・テンプレート・Issue 分割ルール
│   ├── harness-tdd/              # TDD 実装の手順・プランテンプレート
│   ├── harness-review/           # レビュー手順・観点チェックリスト
│   └── harness-bugfix/           # バグ修正の手順・バグレポートテンプレート
├── test/                         # ユニットテスト (node --test)
│   └── e2e/smoke.ts              # 偽モデルで実際の Pi セッションを動かす E2E
└── docs/                         # このドキュメント
```

## 設計方針

### 「手順書」と「強制」の分離

- **Skill（SKILL.md）** は「どうやるか」— 質問の観点、テンプレート、TDD の進め方、レビュー観点 — を記述します。
  Pi は Skill の説明だけをシステムプロンプトに載せ、必要になったときに本文を読むため、コンテキストを圧迫しません。
- **Extension** は「守らなければならないこと」— 承認ゲート、ループ上限、フェーズ順序、テスト結果の真偽 — を強制します。
  LLM が手順を忘れたり省略しようとしても、ツールがエラーを返すか `tool_call` がブロックします。

### エージェントの自己申告に頼らない

| 判定 | 根拠 |
|------|------|
| 承認されたか | UI ダイアログまたはユーザーのコマンドのみ（LLM は承認を記録できない） |
| テストが通ったか | 拡張自身がテストコマンドと `checkCommands` を実行した終了コード |
| テスト後に変更されたか | 合格時点の作業ツリーの指紋（git の HEAD・差分・未追跡ファイルの内容のハッシュ）と遷移時点の指紋を比較。bash 経由の変更も検知。git でない場合は `edit` / `write` の成功を検知 |
| テストを弱めていないか | 実装開始時点からの差分（未追跡ファイルを含む）でテスト削除・スキップ/フォーカス追加・アサーション減少を検知し、理由の記録を必須にしてレビューに回す |
| 承認前にコードを変更していないか | `tool_call` フックでパスを検査してブロック |

制約: プラン承認前など書き込みが禁止されているフェーズでも、bash 経由でファイルを書き換えること自体はブロックしていません（Skill と注入コンテキストで禁止）。
ただし、その変更はテスト合格後の指紋の比較で「未テストの変更」として検知され、レビューの差分（`git diff <基準>`）にも現れます。

### 自然言語での操作と確認

ユーザーはコマンドではなく話しかけて操作します。モデルが依頼を `harness_control` に変換し、ツールは実行前に必ず確認ダイアログを出します。
モデルの判断だけでフローが始まったり、進行中のフローが置き換わったりすることはありません。
ツールはセッションを作れないため、状態を用意して「次セッション待ち」にし、`agent_settled` で新しいセッションを開きます（確認済みなので `autoHandoff: false` でも開く）。
フロー外の通常の会話では harness ツールを `harness_status` と `harness_control` だけにし、ツール定義のトークンを抑えます。

### プロセスごとに独立したセッション

同じ会話の中で計画・実装・レビューを続けると、コンテキストが膨らむうえ、レビューが実装者の思い込みに引きずられます。
そこで各プロセスを独立したセッションで実行し、連携を md ファイル（成果物）に限定しています。

- **状態は `state.json`**: Pi はセッションを切り替えると拡張を再生成するため、状態はセッションではなくファイルに置いています。
  エージェントによる直接編集は `tool_call` でブロックします。
- **切り替えはコマンドから**: セッションの作成 (`ctx.newSession`) はコマンドからしか呼べないため、
  ツールは「次のプロセス待ち」を記録するだけにし、`agent_settled`（Pi が自動では続行しないことが確定した時点）で `/harness next` を実行します。
- **引き継ぎを強制する**: 次のプロセスが読む成果物が無い場合、フェーズ遷移を拒否します。
- **プロセスごとのモデル**: `/harness next` が state.json に「開始中のプロセス」を記録し、新しいセッションで再生成された拡張が
  `session_start` でそれを読み取って `pi.setModel` / `pi.setThinkingLevel` を適用します（そのセッションにだけ効き、Pi の既定値は変えない）。
- **開始メッセージは参照のみ**: 新しいセッションには成果物の「パス」と役割だけを渡し、内容はエージェントに読ませます（前の会話の要約も渡さない）。

### プロジェクトごとに clone して使う

各プロジェクトの `.pi/piHarness/` に clone し、`.pi/settings.json` の `packages` にローカルパスとして登録します（Pi のローカルパッケージ機能）。
Pi は settings ファイルの場所を基準に相対パスを解決するため、プロジェクトを移動しても動きます。
拡張が使う `typebox` と `@earendil-works/*` は Pi 本体が提供するため、clone 先で `npm install` は不要です。

- **状態・成果物・設定の置き場所:** すべてプロジェクト側にあり（`.pi/harness/`, `.pi/harness.json`）、piHarness 本体の clone には書き込みません。
- **本体の編集禁止:** 拡張は自分自身のディレクトリ（`import.meta.url` から求める）への `edit` / `write` をブロックします。
  エージェントがハーネスのルールを書き換えられないようにするためです。
  piHarness 自体を開発するときは、cwd が本体の中なのでブロックしません。

### 状態機械を純粋関数にする

`state.ts` は Pi に依存せず、`(旧状態, 入力) → 新状態` の関数だけで構成しています。
ループ回数・エスカレーション・合流といった最も間違えやすいロジックを、Pi を起動せずにユニットテストできます。
`index.ts` は、ツール引数を検証して状態関数を呼び、結果を永続化して UI に反映するだけの薄い層です。

### コンテキスト注入

`before_agent_start` で、現在のフェーズ・ループ回数・次にやること・前回のブロッキング指摘を非表示メッセージとして注入します。
内容が前回と同じなら注入せず、セッション開始メッセージ（同じ情報を含む）にも注入しません。
古い注入メッセージは会話から削除しません。途中のメッセージを消すとそれ以降のプロンプトキャッシュが無効になるためです（新しい表示に「最新の状態」と明記）。

### 自動圧縮

Pi の既定の自動圧縮はコンテキスト上限の直前で動きます。piHarness は使用率がしきい値を超えた `turn_end` で圧縮を予約し、
次のツール呼び出しをブロックして実行を区切り（`ctx.compact()` は実行中に呼ぶと現在のターンの境界では止まらないため）、
`agent_settled` で圧縮してから、スキル本文と成果物の一覧を含む再開メッセージを送ります。
圧縮で最初のメッセージ（スキル本文）も要約されるため、再開時に送り直すことが重要です。

## Raspberry Pi 5 向けの考慮

- テストのタイムアウトを既定 15 分と長めに設定（`testTimeoutSec`）。
- テスト出力はモデルに末尾 120 行だけ渡し、全文は作業ディレクトリの `logs/` に保存（トークンとメモリの節約）。
- プロセスごとにセッションを分けるため、1 セッションのコンテキストが小さく保たれ、メモリ使用量と応答速度が安定する。
- 部分的なテストは bash で素早く実行し、フェーズ判定のときだけ全体を実行する運用を Skill で推奨。
- レビュー観点に CPU / メモリ / ストレージ書き込み / arm64 対応 / 発熱 / Pi 5 の GPIO（RP1）互換性を含めている。
- 追加のランタイム依存なし（Pi 本体が提供する `typebox` / `@earendil-works/*` のみ使用）。
